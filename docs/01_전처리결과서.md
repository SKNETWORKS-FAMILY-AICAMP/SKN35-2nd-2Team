## 3. 신규 생성 15열

### 3-1. 정답 (1열)

| 컬럼 | 계산식 | 결과 |
|---|---|---|
| **`churn`** | `(총 플레이시간 − 리뷰 시점 플레이시간) < 1시간` → 1 | 이탈 **41.1%** |

관측 창(리뷰 작성 후 180~545일)은 **수집 단계에서 이미 적용**되었습니다. 리뷰를 쓴 지 얼마 안 된 사람은 아직 더 플레이할 시간이 없어 자동으로 이탈로 찍히기 때문입니다.

#### 이탈률 41.1% 가 뜻하는 것

**우리가 선정한 60개 게임에서, 관측 창 안에 리뷰를 작성한 139,658명 중, 리뷰 작성 이후 추가 플레이가 1시간 미만인 사람의 비율**입니다.

다음 표현은 모두 부정확합니다.

| 부정확한 표현 | 이유 |
|---|---|
| "스팀 유저의 41%가 이탈한다" | **리뷰를 작성한 사람**만을 대상으로 합니다. 리뷰 작성자는 전체 유저의 일부입니다 |
| "게임 유저의 41%가 이탈한다" | 우리가 선정한 **60개 게임**에 한정됩니다 |
| "41%가 게임을 영구히 그만두었다" | **"해당 리뷰 이후 1시간 미만"** 입니다. 이후 복귀했을 가능성은 배제하지 못합니다 |

#### 41.1% 는 대푯값으로 사용할 수 없습니다

게임별 이탈률의 분산이 매우 큽니다.

| | 값 | 게임 |
|---|---|---|
| 최저 | **9.7%** | Trailmakers |
| 최고 | **88.8%** | We Were Here Expeditions |
| 게임별 중앙값 | 47.1% | — |
| 게임별 표준편차 | 20.0%p | — |

전체 평균(41.1%)과 게임별 중앙값(47.1%)이 6%p 차이납니다. **리뷰 수가 많은 게임일수록 이탈률이 낮기 때문**입니다(상관 −0.47). 리뷰 수가 많은 게임이 전체 행에서 큰 비중을 차지해 평균을 끌어내립니다.

따라서 보고 시에는 평균 하나가 아니라 **분포와 함께** 제시합니다.

#### 라벨의 한계 — "이탈"의 의미가 장르마다 다릅니다

게임 평가등급별 이탈률에서 예상과 반대되는 결과가 나왔습니다.

| 게임 평가 | 이탈률 |
|---|---|
| 매우긍정 | 37.6% |
| 대체로긍정 | 39.1% |
| 평가나쁨 | 43.6% |
| **압도적긍정** | **46.4%** |

**평가가 가장 좋은 게임의 이탈률이 가장 높습니다.** 장르를 고정해도 동일합니다.

| | 멀티/경쟁 | 싱글 서사 |
|---|---|---|
| 매우긍정 | **20.7%** (최저) | 56.6% |
| 압도적긍정 | 35.2% | **63.7%** (최고) |

해석하면 다음과 같습니다.

- **멀티/경쟁** — 게임이 좋으면 계속합니다. 종료 지점이 없기 때문입니다
- **싱글 서사** — 게임이 좋으면 **끝까지 진행한 뒤 종료**합니다

즉 현재 라벨은 **"흥미를 잃고 이탈"** 과 **"완주 후 종료"** 를 구분하지 못합니다. 구분하려면 게임별 평균 클리어 시간 등 추가 정보가 필요하며, 이는 현재 수집 범위 밖입니다.

이 한계는 결과 해석 시 반드시 함께 제시합니다.

#### 리뷰 길이를 언어별로 정규화한 이유

글자 수가 언어마다 전혀 다른 의미를 가집니다.

| 언어 | 글자 수 중앙값 |
|---|---|
| 영어 | **57자** |
| 브라질 포르투갈어 | 56자 |
| 스페인어 | 56자 |
| 러시아어 | 45자 |
| **중국어(간체)** | **17자** |
| **한국어** | **15자** |

영어가 한국어의 **약 4배**입니다. 한자·한글이 정보 밀도가 높기 때문입니다.

글자 수를 그대로 사용하면 모델이 **"한국어·중국어 리뷰는 성의가 없다"** 고 잘못 학습합니다. 따라서 언어별 중앙값과 표준편차로 정규화한 `review_len_z`를 함께 제공합니다.

```
review_len_z = (글자수 − 해당 언어 중앙값) ÷ 해당 언어 표준편차
```

언어별 기준값은 `lang_stats.json`에 저장하여, **화면(Streamlit)에서도 동일한 기준**을 사용합니다.

#### 표본이 적은 언어 처리 (팀 검토 중 두 차례 발견하여 수정)

**설계 초안** 은 언어별로 중앙값과 표준편차를 모두 계산했습니다. 표본이 적은 언어에서 두 가지 문제가 연달아 나왔습니다.

| | 발견 | 증상 |
|---|---|---|
| **1차** | 아랍어 1건 → 표준편차 계산 불가, 대체값 1.0 | 200자 리뷰의 z 가 **197** |
| **2차** | 노르웨이어 197건이 전부 짧음 → 표준편차 75 | 2000자 리뷰의 z 가 **26.5** (같은 2000자가 영어에서는 3.6) |

2차는 **표본 하한만으로는 못 막는 문제**입니다. 노르웨이어는 197건으로 하한(30건)을 여유 있게 넘겼지만, 그 197건이 모두 짧아서 표준편차가 과소추정됐습니다.

**언어끼리 값을 비교할 수 없다**는 것이 핵심 문제입니다. 이 변수의 목적이 *"언어차를 걷어내고 길이만 보기"* 인데, 정반대 결과가 나온 것입니다.

**해결** — 언어별 표준편차를 쓰지 않고 **전 언어 공통 표준편차**를 씁니다. 언어마다 다르게 쓰는 것은 기본 길이(중앙값)뿐입니다.

성능을 실측해 확인한 뒤 결정했습니다.

| 표준편차 방식 | 노르웨이 2000자 | 영어 2000자 | 격차 | 로지스틱 AUC | 부스팅 AUC |
|---|---|---|---|---|---|
| 언어별 (초안) | 26.50 | 3.62 | 7.3배 | 0.7647 | 0.8181 |
| 전체의 30% 하한 | 10.00 | 3.62 | 2.8배 | 0.7647 | 0.8176 |
| 전체의 50% 하한 | 7.81 | 3.62 | 2.2배 | 0.7647 | 0.8176 |
| **전체 공통 (채택)** | **3.90** | **3.62** | **1.1배** | **0.7647** | 0.8181 |

**언어별 표준편차는 성능 이득이 없었습니다.** 이득이 없는데 버그가 생기는 쪽을 택할 이유가 없어 가장 단순한 방식을 골랐습니다.

수정 후 — 모든 언어가 같은 글자수에 같은 값을 받습니다.

| 언어 | 표본 | 200자 | 2000자 | 8000자 |
|---|---|---|---|---|
| english | 67,115 | +0.28 | +3.84 | +10.00 |
| norwegian | 197 | +0.35 | +3.90 | +10.00 |
| arabic | 1 | +0.31 | +3.86 | +10.00 |
| 미수집 언어 (히브리어 등) | 0 | +0.31 | +3.86 | +10.00 |

**추가 안전장치** — `Z_CLIP = 10.0` 으로 값의 범위를 제한합니다. 학습 데이터에서 여기 걸리는 것은 **261행(0.19%)** 이고 전부 3,000자 이상 리뷰라, *"엄청 길다"* 는 의미는 잘려도 보존됩니다.

트리 모델은 값의 크기가 아니라 순서만 보므로 영향이 없습니다. 그러나 **로지스틱회귀·MLP 는 값을 계수에 곱하므로**, 이 변수 하나가 예측을 지배할 수 있어 상한이 필요합니다.

## 5. 변수 묶음 두 종류

| 게임 이름(`game`) | **포함** | **제외** |
| 사용 목적 | 랜덤 분할 평가 | **게임 단위 분할 평가** |

**근거** — 게임 단위로 train/test를 나누면 학습에 없던 게임이 시험에 등장합니다. 이때 게임 이름은 처음 보는 값이므로 정보가 되지 못합니다. 대신 `genre_group`·`era`·`grade`·`game_age_days` 등 **게임의 속성**으로 판단해야 처음 보는 게임도 예측할 수 있습니다.

**검증 결과** — 두 묶음의 성능 차이가 거의 없었습니다.

| 변수 묶음 | 랜덤 분할 | 게임 단위 분할 |
|---|---|---|
| A셋 (게임 이름 포함) | AUC 0.820 | 0.754 |
| B셋 (게임 속성만) | AUC **0.817** | **0.748** |

게임 이름을 제거해도 성능이 유지된다는 것은, 모델이 **게임 이름을 암기한 것이 아니라 게임 속성을 학습**했음을 시사합니다.

## 7. 재현성

| 항목 | 내용 |
|---|---|
| 원본 | `03_수집/steam_raw.csv` (수정 금지) |
| 전처리 | `04_전처리/preprocess.py` |
| 실행 | `uv run python preprocess.py` |
| 결과 | `dataset.csv` · `lang_stats.json` · `dataset_meta.json` |

**원본만 있으면 언제든 동일한 결과를 재생성**할 수 있습니다. 전처리 기준을 변경할 경우(예: 이탈 판정 1시간 → 2시간) `preprocess.py`의 `CHURN_HOURS` 상수 한 곳만 수정하면 됩니다.

### 버전 관리

전처리 규칙이 바뀌면 `preprocess.py`의 `VERSION` 을 올리고 `CHANGELOG` 에 사유를 적습니다. 실행하면 `dataset_meta.json` 이 함께 생성됩니다.

```json
{ "전처리_버전": "1.2", "이번_변경": "리뷰 길이 표준편차를 전 언어 공통으로 ...",
  "생성일시": "2026-08-26 15:57", "행수": 139658, "이탈률": 0.4112 }
```

**모델·화면 담당자가 자기 파일이 최신인지 눈으로 확인**할 수 있어야 하기 때문입니다. 파일 크기가 68MB라 매번 다시 받게 하면 팀 전체가 시간을 낭비합니다. `lang_stats.json` 에도 `_version` 이 들어갑니다.

| 버전 | 날짜 | 변경 |
|---|---|---|
| 1.0 | 2026-08-25 | 최초 — 라벨·파생변수 15열, 누수 8열 제외 |
| 1.1 | 2026-08-26 | 표본 30건 미만 언어의 길이 기준을 전체 통계로 대체 (§3-4). dataset.csv 1행 변동 |
| **1.2** | 2026-08-26 | 리뷰 길이 표준편차를 **전 언어 공통**으로 변경 + `Z_CLIP = 10` (§3-4). 성능 지표 변동 없음 (부스팅 0.819→0.820, 로지스틱 0.797→0.798 = 재학습 오차 범위) |

이번 수정에서 **"1행만 달라졌다"를 확인할 수 있었던 것** 자체가 이 구조의 효과입니다. 원본이 보존돼 있고 전처리가 한 파일에만 있어서, 예전 방식으로 다시 계산해 비교할 수 있었습니다. 전처리가 노트북 셀에 흩어져 있었다면 영향 범위를 알 수 없어 팀원 3명이 각자 작업을 다시 해야 했을 것입니다.
